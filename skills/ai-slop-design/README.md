# ai-slop-design

Pages built by agents look alike: a purple-to-blue gradient, Inter, a centred hero over three icon cards, glass panels, small tracked caps above every heading, an arrow glued to every link. Each choice is a reflex, the default a model reaches for on any brief. This skill builds pages whose look comes from their subject, and sweeps existing frontend code for those reflexes, for text that fails contrast, for layouts that break on phones, and for styles copied where one component would do.

*Versione italiana in fondo: [Italiano](#italiano).*

## Install

```sh
npx skills@latest add guarriellocristianmichele/supah-skills -s ai-slop-design
claude plugin install ai-slop-design --marketplace guarriellocristianmichele/supah-skills --scope user
```

Every route and scope is in the [repository README](../../README.md#installation-1-minute-setup). Requirements: Python 3.10 or newer on `PATH`, standard library only.

### Works best with screenshots

The scanner reads source, so it can't see what only the rendered page shows: a hero that sits dead centre, text over a photo, elements that overlap at 390 pixels, a grid that turned into a wall of cards. Give the agent a browser tool and, once you allow it on screen, it researches on its own: craft looks at current work in the category and the competitors in your brief, opens font specimens and checks every stock photo URL, and every mode looks at the page (an audit, at a sample of surfaces) at 390, 768 and 1440 pixels, checks for horizontal scroll, and judges the screenshots against the direction and the category's floor. The question offers an isolated Playwright browser (recommended), your own Chrome with your sign-ins, or no browser. In Claude Code, any of these works: the [Playwright plugin](https://github.com/microsoft/playwright-mcp), Claude in Chrome, or the built-in browser. Without one, the skill still runs and the report says the render was not checked.

## Use

```text
/ai-slop-design craft a site for a bicycle repair workshop in Turin
/ai-slop-design sweep src/app/page.tsx src/components/*.tsx
/ai-slop-design audit
/ai-slop-design plan
/ai-slop-design sweep B1
/ai-slop-design sweep all
/ai-slop-design publish
/ai-slop-design craft src/app/pricing/page.tsx
```

It is user-invoked, so it costs nothing in sessions where you don't call it.

On a whole platform the modes make one flow: `audit` → `plan` → `publish` → `sweep B<n>`, with `craft <surface>` for each handoff batch, then `audit` again to close what was fixed. Nothing changes in the source until a batch is swept or restyled, and `publish` is only needed when someone else will work the batches.

- `craft` names the subject, audience and job, writes the page it would build by reflex and sets that answer aside, then commits to a direction (palette, type, layout, one memorable element, one motion moment) with a reason for each axis. It builds, sweeps its own output, checks screenshots, and records the direction in `.slop-design/history.md` so the next page in the project goes somewhere else.
- `sweep` scans HTML, CSS, SCSS, JSX/TSX, Vue, Svelte and Astro files, judges every hit (`reflex`, `chosen` with a reason, or `fp`), fixes the reflexes and reads the page as a whole for what no pattern sees. A page that sits in a whole lane (cream and clay, near-black with one neon accent, the SaaS card kit…) is kept as a `handoff` and named in the report with the command that works it.
- `craft <surface>` restyles an existing page, usually a sweep's handoff: it reads the brief from the page, lists every string, link, form and handler before touching anything, and checks the new direction against the lane the page sat in, revising any axis that lands in it again. Content and behaviour stay as they were; only the look changes, and the restyled files are compared with that list before the sweep. Given a page from a handoff batch of the plan, it closes the batch once its last page is restyled: the findings become `fixed` and the batch `done`, and the tracker is left alone.
- `audit` is for a whole platform, and it changes no source file. It groups the frontend into surfaces (each route with the components only it uses, plus one `shared` unit for the rest), detected from Next.js, Nuxt, SvelteKit, Astro or react-router conventions or by directory, scans every file in one run, and judges each surface in its own context through orchestrate. Verdicts, findings and a keep file stay in `.slop-design/`, so sweep reuses them. It screenshots a sample of routes (one per category and the five with the most hits on the page, duplication left out) and lists the rest as render not checked. The report opens with `COMPLETE: N/N surfaces` or `PARTIAL: k/N surfaces`. Run `audit` again after fixes, or after an interrupted run, and it reconciles the ledger with a fresh scan: findings whose hit is gone close as fixed, returning ones reopen, hits nobody judged yet are added, and surfaces already judged are not judged again. There is no separate verify mode.
- `plan` turns an audit's open findings into ordered batches, and it changes no source file either. It rescans first, so findings that no longer reproduce are closed or marked stale before anything is batched. Token/component batches come first: duplicated class strings, CSS blocks and untokened colours become one token or component, added in an expand batch, swapped in by migrate batches of a few surfaces each, and cleaned up in a contract batch, so the platform keeps working between batches. Then one surface batch per surface for its reflexes and copy, and one handoff batch per lane, worked with `craft <surface>`. Each batch in `.slop-design/plan.md` lists its files, findings, what it depends on and its checks: the rescan passes with the keep file, the content is unchanged, and no page scrolls sideways at 390, 768 and 1440 pixels where it was rendered. Every open finding lands in exactly one batch or is rejected with a reason.
- `sweep B<n>` fixes one batch of the plan: only the batch's files, with the audit's keep file, so hits judged once are not judged again. Once the batch's checks pass, its findings become `fixed` and the batch `done` in `.slop-design/`; sweep never writes to the tracker. A plain `sweep` with no files, on a repo above 5 surfaces or 40 frontend files, asks first: audit first (recommended), sweep everything, or sweep one path. A smaller repo is swept as before, without the question.
- `sweep B2 B5`, `sweep #<map>` or `sweep all` works several batches in parallel through orchestrate, each in its own git worktree, merged into one integration branch, `slop/design-<sha>`, in the order their dependencies set. It takes the token/component and surface batches whose findings are all scanner reflexes with a fix; handoff batches and batches with judgment, copy or lane findings are listed with their command, since they need a person's choice. After the merges it rescans the platform, reconciles the ledger, runs the render checks if you allowed a browser (asked once), and asks before opening one pull request that closes the done issues.
- `publish` turns the plan's batches into issues, one per batch plus a map issue that lists them in order, and changes no source file. It first reads the issues it already opened: one closed as done marks its findings fixed in the ledger, one closed as not planned marks them `rejected:wontfix`. It shows the drafts, numbered, and creates nothing until you approve them. Each issue carries its files, its findings with evidence linked at the commit they were scanned at, the keep lines and the checks, so it can be worked from a clone without the ledger; a finding read in a file you had not committed gets no link (a duplication group loses it only for its uncommitted files), and `publish` offers to commit and audit again first. A hidden marker lets the next `publish` update the same issue instead of opening a second one. It uses `gh` on GitHub, the tracker and labels of [mattpocock/skills](https://github.com/mattpocock/skills) when they are set up, and files in `.slop-design/issues/` otherwise; each file's first line, `State: open`, `done` or `wontfix`, is its state, `sweep B<n>` sets it to `done`, and `sweep .slop-design/issues/map.md` works the local map. With those skills installed, the report also suggests `/to-tickets` for token and component work and `/to-spec` for a lane over several pages; it never runs them.
- Every mode starts from the category of what is being built: local business site, SaaS marketing site, SaaS product UI, mobile app, e-commerce, or portfolio and campaign. Each category has a frame of conventions visitors rely on (hours one tap away, real prices, the platform's navigation, guest checkout), the room where the design can go far, an accessory budget for decoration, and its own accessibility floor. Creativity goes inside the frame.

## What the scanner checks

45 rules in nine categories. `python scripts/designscan.py rules` lists them with their tiers.

| Category | Examples |
|---|---|
| colour | purple gradients, stock Tailwind swatches, cream with clay, literal black and white, text below WCAG contrast |
| type | reflex fonts, one accented word in a heading, eyebrows, small tracked caps, mono labels |
| surface | gradient text, glass cards, coloured glows, accent stripes, the default shadcn card, one radius everywhere |
| layout | three-column icon-card grids, 01/02/03 markers, stat banners, viewport-high heroes, drawn browser windows |
| glyph | emoji icons, `A · B · C` strings, glued arrows, `WORD — fragment` labels, pulsing dots |
| motion | `transition: all`, a reveal on every section, bounce easing, hover scale everywhere, no reduced-motion path |
| placeholder | Acme, Jane Doe, 555 numbers, `href="#"` |
| responsive | no viewport meta, fixed pixel widths, multi-column grids on phones, hover-only content, text under 12 pixels, `100vw` |
| duplication | the same long class string in three places, identical CSS blocks, one hex colour repeated instead of a token |

Every judged hit is a verdict in your own log (`sweep` records them from the diff, `audit` from its findings and keep lines), and after 30 verdicts on a rule its tier follows the precision measured on your projects; `designscan.py learn` shows each rule, `audit` asks you to confirm a sample, and `export` writes the counts, with no code, for an issue ([ADR 0018](../../docs/adr/0018-every-scanner-learns-its-tiers-from-the-users-verdicts.md)). A hit is a candidate, never a verdict: a real brand colour, a real sequence of steps or a live status dot is kept with its reason. Tiers come from judged precision ([ADR 0011](../../docs/adr/0011-design-reflex-tiers-from-judged-precision.md)), and the scanner reads source only; contrast is checked where text and background are declared together.

## Italiano

Le pagine costruite dagli agenti si somigliano tutte: gradiente viola-blu, Inter, hero centrato sopra tre card con icona, pannelli di vetro, maiuscoletto spaziato sopra ogni titolo, una freccia attaccata a ogni link. Ognuna è una scelta di riflesso, quella che un modello fa per qualunque brief. Questa skill costruisce pagine il cui aspetto viene dal soggetto, e controlla il codice frontend esistente per questi riflessi, per i testi con contrasto insufficiente e per gli stili copiati dove basterebbe un componente.

Installazione: `npx skills@latest add guarriellocristianmichele/supah-skills -s ai-slop-design`, oppure come plugin di Claude Code con `claude plugin install ai-slop-design --marketplace guarriellocristianmichele/supah-skills --scope user`. Si avvia a mano, quindi non occupa contesto nelle altre sessioni.

Su una piattaforma intera le modalità formano un unico percorso: `audit` → `plan` → `publish` → `sweep B<n>`, con `craft <surface>` per ogni lotto di `handoff`, poi di nuovo `audit` per chiudere ciò che è stato corretto. Il codice non cambia finché un lotto non viene corretto o rifatto, e `publish` serve solo quando i lotti li lavorerà qualcun altro.

- `craft <brief>` scrive prima la pagina che verrebbe di riflesso e la scarta, poi sceglie palette, caratteri, layout, un solo elemento memorabile e un solo movimento, ognuno con il suo motivo. Costruisce, controlla il proprio codice e gli screenshot, e annota la direzione in `.slop-design/history.md` perché la pagina successiva vada altrove.
- `sweep [file…]` legge HTML, CSS, JSX/TSX, Vue, Svelte e Astro, giudica ogni segnalazione (riflesso, scelta voluta con il motivo, falso positivo), corregge i riflessi e guarda la pagina intera per ciò che nessuno schema vede. Una pagina che sta tutta in un filone estetico (crema e argilla, nero con un solo accento al neon, il kit di card SaaS…) viene segnata come `handoff` e il report indica il comando per rifarla.
- `craft <surface>` rifà l'aspetto di una pagina esistente, di solito un `handoff` di `sweep`: ricava il brief dalla pagina, elenca testi, link, form e gestori di eventi prima di toccare qualcosa, e controlla la nuova direzione contro il filone in cui la pagina stava, rivedendo ogni scelta che ci ricade. Contenuti e comportamento restano quelli di prima, cambia solo l'aspetto, e i file rifatti vengono confrontati con quell'elenco prima del controllo finale. Se la pagina viene da un lotto di `handoff` del piano, chiude il lotto quando ne ha rifatto l'ultima pagina: le segnalazioni diventano `fixed` e il lotto `done`, senza toccare il tracker.
- `audit [percorso]` serve per una piattaforma intera e non modifica nessun file sorgente. Divide il frontend in superfici (ogni route con i componenti che usa solo lei, più un'unità `shared` per il resto), riconosciute dalle convenzioni di Next.js, Nuxt, SvelteKit, Astro o react-router oppure per cartella, analizza tutti i file in un solo passaggio e giudica ogni superficie in un contesto separato tramite orchestrate. Verdetti, segnalazioni e file delle eccezioni restano in `.slop-design/`, così `sweep` li riusa. Fa gli screenshot di un campione di route (una per categoria e le cinque con più segnalazioni sulla pagina, duplicazioni escluse) ed elenca le altre come non controllate a schermo. Il report si apre con `COMPLETE: N/N surfaces` oppure `PARTIAL: k/N surfaces`. Se rilanci `audit` dopo le correzioni, o dopo un'esecuzione interrotta, confronta il registro con una nuova analisi: le segnalazioni sparite passano a `fixed`, quelle ricomparse tornano aperte, le nuove vengono aggiunte e le superfici già giudicate non vengono giudicate di nuovo. Non serve una modalità di verifica a parte.
- `plan` trasforma le segnalazioni aperte di un `audit` in lotti ordinati, e anche lui non modifica nessun file sorgente. Prima rianalizza il codice, così le segnalazioni che non si riproducono più vengono chiuse o segnate come superate prima di formare i lotti. Vengono prima i lotti di token e componenti: classi ripetute, blocchi CSS duplicati e colori senza token diventano un solo token o componente, aggiunto in un lotto di espansione, sostituito alle copie da lotti di migrazione di poche superfici ciascuno e ripulito in un lotto di contrazione, così la piattaforma funziona tra un lotto e l'altro. Poi un lotto per superficie, con i suoi riflessi e i suoi testi, e un lotto di `handoff` per ogni filone estetico, da rifare con `craft <surface>`. Ogni lotto in `.slop-design/plan.md` elenca file, segnalazioni, dipendenze e controlli: la nuova analisi passa con il file delle eccezioni, i contenuti restano uguali e nessuna pagina scorre di lato a 390, 768 e 1440 pixel dove è stata renderizzata. Ogni segnalazione aperta finisce in un solo lotto, oppure viene scartata con un motivo.
- `sweep B<n>` corregge un lotto del piano: solo i file del lotto, con il file delle eccezioni dell'`audit`, così le segnalazioni già giudicate non vengono giudicate di nuovo. Quando i controlli del lotto passano, le sue segnalazioni diventano `fixed` e il lotto `done` in `.slop-design/`; `sweep` non scrive mai nel tracker. Uno `sweep` senza file, in un repository con più di 5 superfici o 40 file frontend, chiede prima come procedere: prima un `audit` (consigliato), tutti i file, oppure un solo percorso. In un repository più piccolo lo `sweep` parte subito, come prima.
- `sweep B2 B5`, `sweep #<map>` o `sweep all` lavora più lotti in parallelo tramite orchestrate, ognuno nel suo worktree git, uniti in un integration branch nell'ordine delle dipendenze. Prende i lotti di token, componenti e superfici le cui segnalazioni sono tutte riflessi dello scanner con una correzione; i lotti di `handoff` e quelli con segnalazioni di giudizio, testo o filone restano fuori, elencati con il loro comando. Alla fine rianalizza la piattaforma, aggiorna il registro, fa i controlli a schermo se hai permesso il browser (lo chiede una volta) e chiede prima di aprire una pull request che chiude le issue completate.
- `publish` trasforma i lotti del piano in issue, una per lotto più una issue mappa che li elenca in ordine, e non modifica nessun file sorgente. Prima legge le issue che ha già aperto: una chiusa come completata segna le sue segnalazioni come `fixed` nel registro, una chiusa come non pianificata le segna `rejected:wontfix`. Mostra le bozze numerate e non crea nulla finché non le approvi. Ogni issue riporta i file, le segnalazioni con le prove collegate al commit analizzato, le eccezioni e i controlli, così si può lavorare anche da un clone senza registro; una segnalazione letta in un file non ancora committato resta senza link (per un gruppo di duplicati, solo nei suoi file non committati), e `publish` propone prima di fare il commit e rilanciare `audit`. Un marcatore nascosto permette al `publish` successivo di aggiornare la stessa issue invece di aprirne un'altra. Usa `gh` su GitHub, il tracker e le etichette di mattpocock/skills quando sono configurati, altrimenti file in `.slop-design/issues/`; la prima riga di ogni file, `State: open`, `done` o `wontfix`, è il suo stato, `sweep B<n>` la porta a `done`, e `sweep .slop-design/issues/map.md` lavora la mappa locale. Con quelle skill installate il report suggerisce anche `/to-tickets` per il lavoro su token e componenti e `/to-spec` per un filone estetico su più pagine, senza mai avviarli.
- Tutte le modalità partono dalla categoria del prodotto (sito vetrina, sito marketing SaaS, interfaccia SaaS, app mobile, e-commerce, portfolio e campagne): per ognuna ci sono le convenzioni da rispettare, lo spazio per la creatività, quanto decorare e i requisiti minimi di accessibilità. La creatività resta dentro la cornice.
- Ogni segnalazione giudicata diventa un verdetto nel tuo registro locale: `sweep` li ricava dal diff, `audit` dalle segnalazioni e dalle eccezioni. Dopo 30 verdetti su una regola il suo livello segue la precisione misurata sui tuoi progetti; `designscan.py learn` mostra ogni regola, `audit` ti fa confermare un campione ed `export` scrive i conteggi, senza codice, da allegare a una issue.
- Funziona meglio con gli screenshot. Lo scanner legge il codice, quindi non vede ciò che appare solo nella pagina renderizzata: un hero piantato al centro, testo sopra una foto, elementi che si sovrappongono a 390 pixel. Con un browser a disposizione (il plugin Playwright, Claude in Chrome o il browser integrato) e dopo la tua autorizzazione a schermo, l'agente fa ricerca da solo: in `craft` guarda i siti attuali della categoria e i concorrenti del brief, apre i campioni dei font e verifica le foto stock; in tutte le modalità guarda la pagina (in `audit`, un campione di superfici) a 390, 768 e 1440 pixel, controlla lo scroll orizzontale e giudica gli screenshot. La domanda propone un browser Playwright isolato (consigliato), il tuo Chrome con i tuoi accessi, oppure nessun browser. Senza browser la skill funziona lo stesso e il report dice che la resa non è stata controllata.
- Lo scanner ha 45 regole in nove categorie, contrasto WCAG, responsive e stili duplicati compresi. I livelli vengono dalla precisione misurata sui casi giudicati.
